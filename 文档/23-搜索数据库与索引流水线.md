# 搜索数据库与索引流水线

> 详细目标设计。当前 0005 已落地六张搜索表及两个扩展，按项目原子替换、共享租约/分页，实际名称与限制见 [第 32 号](32-搜索实现与多节点契约.md)。本页多代表/别名/蓝绿切换等未完成部分保留为后续目标，不表示已创建所有下列表。

## 数据分层与表结构

沿用 PostgreSQL 18；依赖快照和任务仍按现有表存储。正文允许进入搜索域，禁止回写 `scan_mods`、`declared_dependencies` 或 `scans.result`。以下表名是设计契约，落地前需结合目录迁移确认。

| 表 | 核心字段与唯一约束 | 用途/索引 |
| --- | --- | --- |
| project_documents | id、project_source_id、field(title/summary/body)、language、source_hash、translation_revision、review_state、raw_object_key、cleaned_object_key、cleaner_revision、created_at | 不可变正文/译文版本；来源+字段+语言+内容/派生版本唯一；对象存储保存大文本 |
| search_aliases | project_id、alias_raw、alias_normalized、alias_kind、provenance_ref、review_state | 名字、社区俗称、slug/包内 ID 分型；精确 B-tree，名称 trigram GIN；跨项目允许同名 |
| search_generations | id、config_revision、catalog_watermark、status(building/active/retired/failed)、created_at、activated_at | 分词/模型全量重建代次；只允许一个 active，通过控制行锁事务切换 |
| search_project_heads | generation_id、project_id、document_set_hash、source_revision、translation_revision、projection_revision、indexed_at | 当前项目可检索版本；代次+项目唯一；绑定允许的文档集合 |
| search_chunks | id、generation_id、project_id、document_id、document_set_hash、field、language、ordinal、start_char、end_char、token_count、clean_text、tokens_vector、tokenizer_revision、chunker_revision | 代次+文档+切块版本+ordinal 唯一；GIN(tokens_vector)，B-tree(代次/项目/文档集合) |
| embedding_models | id、model_name、model_revision、tokenizer_revision、dimensions、normalization、distance、runtime_revision、license_ref | 固定模型空间，不只存可变的模型名字 |
| search_embeddings_bge_m3 | chunk_id、generation_id、model_id、input_hash、embedding vector(1024)、created_at | 块+模型唯一；FK 连接块；HNSW(vector_cosine_ops)按实测建立 |
| search_index_jobs | id、kind(project_update/rebuild/delete)、project_id、source_revision、target_generation_id、idempotency_key、state、lease_until、claim_token、attempts、error | 来源更新幂等/重试；lease 和状态字段遵守第 19 号，不复用 collection_jobs 的 JAR 请求 JSON |
| outbox | id、aggregate_id、event_type、revision、payload、created_at、dispatched_at | 和目录/译文更新同事务提交，索引消费后确认 |
| search_sessions | id、query_fingerprint、filters_hash、generation_id、config_revision、ranked_project_refs、expires_at | 有界候选列表的稳定短期分页；不默认保存原始敏感查询文本 |

`project_documents` 的文档集合可以包含多个来源与语言；`document_set_hash` 从被选中文档版本列表确定性计算。即使只更新一段译文，也需要提交新的项目投影版本，避免 API 同时展示新译文和旧原文关联。

表内还需记录覆盖状态：正文不存在、无权收录、待同步、清洗失败、处理截断、语义待生成。缺失正文不能变成空字符串并显示“全文已建立”。`search_project_heads` 的就绪状态和统计字段在实际迁移中显式建列，不能由 UI 猜测。

模型升级若维度不同，建立对应维度的新向量表/索引并通过适配器统一读取；不能把不同维度塞进同一个固定 `vector(1024)`，也不能把不同 revision 的向量跨空间比较。即使维度相同，切换模型也必须重算对应代次的全部向量和查询向量。

## 中文词法投影

索引 worker 读取已清洗的段落，使用固定 jieba 版本、用户词典哈希、规范化/短词策略版本分词。文档与查询共用唯一 tokenizer；以 `simple` 配置生成词法向量，应用层对名称、简介、正文分别设置权重。`tokens_vector` 不是从原始整篇中文直接 `to_tsvector` 得到。

查询默认是自然文本，不开放 PostgreSQL `tsquery` 语法。先做长度/词数限制，使用参数绑定及受控查询构造器；用户的引号、冒号、`&`、`!`、反斜杠不得变成任意 SQL/解析器指令。需要 OR 扩展的同义词组由同一查询编译器构造，受版本化词表和候选上限控制。

原始正文/译文和清洗文本始终保留各自哈希。摘要高亮返回字符偏移和文字片段，由 Vue 文本节点渲染。若清洗/简繁规范化改变了偏移，建立映射或在最终原清洗文本上重新定位；不能直接套用 token 序号。

## 增量任务与一致性

1. 上游适配器更新项目/版本/正文；本地目录事务同时写 outbox。旧服务跨库不能假装有分布式事务，使用其单调 revision/游标拉取并做周期对账；删除和审核撤回必须有事件或 tombstone。
2. 消费者按项目+目标代次合并重复事件，幂等键包含来源修订/内容哈希。新的文本派生文档写新行，不覆盖旧行；翻译完成/人工修订也产生新事件。
3. 文本清洗和全文索引可先完成，向量后台批量生成。每一阶段写明确就绪状态；混合请求只能读当前文档集合的向量，不能拿过期文本向量凑数。
4. 新块/向量构建期间不改 active head。完成一个可发布项目投影后，短事务检查来源修订、claim_token、当前版本，再原子切换 head；晚完成的旧任务只可丢弃/记录 superseded，不得覆盖新版本。
5. worker 超时、崩溃、取消遵守租约恢复；推理/外部正文调用有独立超时、批大小/字节上限和重试退避。目录和译文服务继续承担各自职责，索引 worker 不再抓一遍未授权网页或重译正文。
6. 下架、私有化、审核撤回立即更新权威可见性；所有检索路径、相似资源、缓存/分页取回时都重新关联可见性和 head，不等待异步删索引。随后清除索引、会话引用和不再允许保留的文本/向量，保留必要审计。
7. 可见性与正文改版不同：普通改版允许带水位展示上一份有效投影；撤回/敏感删除必须立即禁止访问旧投影。`source_revision`/`indexed_at` 明确返回，不能把上一版当实时最新版。

词法和语义可以分阶段就绪，但每次发布的 head 都描述确切文档集合及各路覆盖状态。公开默认只索引公共/可发布内容；内部未审核或私有资料不混入公共 ANN 索引，避免共享候选和缓存泄漏。

## 全量重建与回滚

新增 building generation → 按目录水位回填 → 持续消费水位之后的 outbox → 对账缺页/删除 → 质量评测与覆盖率检查 → 控制行锁事务切换 active generation → 在途会话按明确策略失效 → 观察 → 宽限期后回收旧代次。

索引器记录来源版本，不用“按时间大概重跑一遍”防丢更新。分词词典、清洗/切块版本、embedding 模型变更均触发相应重建。回滚保留可查询的上一代并重新追平变更；不能回滚到会重新暴露已撤回资源的快照。事实 scan 不参与索引回滚。

## 向量查询与筛选

第一批数据先跑精确最近邻作为正确性基线；HNSW 是容量测量后的优化。按模型空间、当前代次、公开状态和业务筛选限制候选。pgvector ANN 的过滤可能发生在索引候选之后，不能“取全库前 20 再筛”就承诺返回 20 个符合条件结果。

实现时比较索引迭代扫描、有界过采样、按资源类型/代次分区和小候选集精确距离计算；始终复核 MC/加载器的同一文件条件。每种方案同时报告筛选后的 recall@K、时延和候选不足比例。不能跨模型混用距离，也不能把调大 ef_search 当作覆盖率验收。

## 容量与部署预算

粗估必须以项目、语言、块三维计数：100 万项目 × 2 种语言 × 平均 8 块 = 1,600 万向量。1024 维 float32 原始向量约 65.5 GB（十进制），还不含行/向量头、HNSW、清洗文本、GIN、WAL、备份和重建双份空间。不是“加个向量字段占不了多少”。

先抽 1 万项目测正文 P50/P95 长度、块数、分词耗时、嵌入吞吐与索引膨胀；扩展到 10 万项目测筛选召回与并发。保留预算内的语言/正文版本，历史原文可冷存；不任意截断后宣称全量全文。确认合法同源内容后可按内容哈希去重推理，仍保留来源关联和权限判断。

搜索容量测试建议独立基线：数据库 8 vCPU/32 GiB/SSD；embedding 服务硬件单列，先测 CPU 再决定 GPU，不能套用第 10 号采集 API 的 2 vCPU/4 GiB 目标。目标时延见第 24 号，未实测不承诺 QPS。

生产启用前，构建/选择明确支持 PostgreSQL 18 的 pgvector 镜像或扩展包，固定版本/镜像摘要，单独迁移启用 `vector` 与 `pg_trgm`；运行角色不赋予安装扩展权限。现有原生 PG compose 不能不改就运行向量迁移。SQLite 只做无向量业务单测，不能替代 PG 中文全文、GIN、HNSW 和并发验收。

达到容量或延迟瓶颈后，先检查 SQL/过滤选择率、块数、索引与推理缓存，再决定是否迁出专用搜索/向量引擎。触发评估条件是已按第 24 号复现的 SLO/召回率不达标或容量超预算；不按“百万条”单一数字盲目换引擎。SearchPort 屏蔽实现，PostgreSQL 仍是资源/事实源，派生索引可全量重建。

## 权限、缓存和观测

- 查询缓存键包含规范查询、完整筛选、语言、权限范围、代次、检索配置/模型版本；embedding 查询缓存另含模型和预处理版本。不能只用中文查询串作为键。
- 命中缓存和分页仍复核可见性；内容撤回事件主动失效。敏感查询不默认写原始日志，指标按匿名分类聚合。
- 指标：正文/译文覆盖率、词法/向量就绪率、索引水位与滞后、outbox 最老年龄、失败/过期任务、推理批耗时、缓存命中、各路召回数量、降级比例、筛选后 ANN recall、端到端 P50/P95/P99。
- 备份遵守第 04 号：正文与来源快照不可只依赖重抓；派生向量可以重建，但必须备份固定模型/词典/配置清单及恢复估算。实际恢复验收必须覆盖有删除/译文修订的项目。
