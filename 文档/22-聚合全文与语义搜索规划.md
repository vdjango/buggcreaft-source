# 聚合全文与语义搜索规划

> 当前基线已实现：原文/当前译文全文、中文向量、混合/相似及多节点，详见 [第 32 号](32-搜索实现与多节点契约.md)。下文保留长期目标，未落地的别名库、全站聚合、人工留出集等不视为完成；实际模型/表名/接口以第 32 号为准。输入为本仓库 src/mc_translate，“旧服务”指迁入的同一所有者。

> 2026-11-09 长期设计。数据库和索引目标见第 23 号，API/质量门槛见第 24 号；实际验收见第 32 号。

## 产品范围与阶段定位

平台由资源目录、译文、制品依赖、聚合搜索四个协作模块组成，共用资源标识和 PostgreSQL，按进程分离抓取、翻译、采集、索引和推理。搜索覆盖模组、资源包、光影、整合包，不局限于已有依赖扫描的 JAR。资源尚未扫描仍可被搜索，但必须显示依赖尚未采集；不能为了等包内扫描而阻断资源发现。

这里的聚合是把获准收录的多个来源同步到自己的资源目录和索引，再用同一个入口检索。请求时不临时逐一访问 CurseForge/Modrinth、不临时翻译全部结果。来源暂时不可用时，仍可检索已收录内容，并返回索引时间与覆盖范围；不承诺覆盖上游全站。

搜索是 P2 阶段的独立交付项，不能用“目录有一个搜索框”代替全文和语义能力。P0 可信依赖采集继续保持；P1 先具备目录和正文增量输入；P2 依次验收名称/别名、正文全文、语义及混合检索。具体任务编号见第 24 号。

## 用户需求拆分

| 编号 | 能力 | 例子 | 边界 |
| --- | --- | --- | --- |
| SRCH-01 | 多源聚合 | 同时检索已收录的 Modrinth、CurseForge 和旧站项目 | 展示来源，不能按同名擅自合并项目 |
| SRCH-02 | 名称与别名 | 英文原名、中文译名、社区俗称、slug、mod ID | 包内 ID 只来自 scan；社区别名需来源/审核 |
| SRCH-03 | 正文全文 | 正文提到“支持容器整理”，标题没有也能命中 | 原文及当前可发布译文均入索引，不只搜索简介 |
| SRCH-04 | 模糊匹配 | 英文拼写遗漏、近似名字 | 字符相近单独标记，不冒充语义相关 |
| SRCH-05 | 语义查询 | “想让箱子里的物品自动分类” | 检索功能相近的真实文本，不凭模型编资源或断言兼容 |
| SRCH-06 | 相似资源 | 在项目详情点“功能相近” | 排除自身/已确认同源副本；可叠加 MC/加载器筛选 |
| SRCH-07 | 筛选与排序 | 资源类型、来源、MC 版本、加载器、运行侧、语言 | 兼容性筛选使用同一版本/文件记录，见第 24 号 |
| SRCH-08 | 结果解释 | “中文正文命中”并显示实际段落 | 文字命中可高亮，语义命中显示相关段落；不生成伪引文 |

这些示例是验收意图，不是当前搜索结果。中文标题不存在时显示真实原名和“暂无中文译名”，不能声称所有内容都已有中文翻译。

## 先审计旧实现，再决定复用

本次只读检查 `minecraft-translation-platform`：

- `src/mc_translate/api.py: catalogue`：`/v1/catalog/search` 搜索目录标题/简介，以及指定语言的 `localized_catalogue`；长度至少 3 的查询使用 FTS5 trigram，短查询走 LIKE；按资源 key 分页，并非全文相关度排序。
- `src/mc_translate/store.py`：`catalogue_fts` 投影为 `title + summary`，`localized_catalogue` 回填来自 `field='summary'` 的译文。正文刻意没有进入这套小目录索引。
- `tests/test_languages.py` 已有语言隔离的目录检索测试。它证明旧站有中文简介检索，不能证明有正文检索、中文分词或语义向量能力。

因此复用旧服务的目录、正文/译文获取、原文哈希、缓存和权限契约；先确认能否提供完整正文和增量事件。若现有接口缺少这些内容，先在旧服务发布版本化导出接口；不能拿仅返回简介的搜索结果当全文输入，也不直读其生产 SQLite。新平台创建唯一搜索索引和编排所有者，不复制旧 SQLite 搜索 SQL，不新增第二套译文模型客户端。

## 检索技术选择

第一版采用 **PostgreSQL 18 + 原生全文检索/GIN + pg_trgm + pgvector**，后端沿用 FastAPI，页面沿用 Vue 3/TypeScript。事实与索引共库、分表、分权限；向量和词法索引是可重建派生数据。扩展不是当前已安装依赖，现有 `compose.yaml` 仍只是原生 PostgreSQL 开发服务。

| 检索层 | 首选实现 | 作用 |
| --- | --- | --- |
| 精确身份/名字 | 规范化精确键 + B-tree | 来源 ID、slug、已验证 ID、名字/别名精确命中 |
| 中文与英文全文 | 应用层中文分词 + PostgreSQL `tsvector`/GIN，`ts_rank_cd` | 标题、简介、正文分字段检索与排序 |
| 字符近似 | `pg_trgm`，主要用于名称/别名 | 拼写和字符串相似；不在所有正文上盲建 trigram |
| 语义召回 | 独立 embedding 服务 + pgvector 余弦检索 | 中文自然语言、跨语言近义、相似功能 |
| 合并排序 | 按项目去重后 RRF，精确身份保留优先级 | 不直接相加量纲不同的全文分数和向量距离 |
| 精排 | 后续按质量/时延评测决定是否使用 reranker | 不作为首版上线依赖 |

PostgreSQL 默认配置不能直接当作合格的中文分词方案。先选 jieba 的搜索模式和 MC 专用词典，文档与查询经过同一个分词器、规范化和词典版本，再交给 `simple` 文本配置。英文原词与大小写归一化、连字符 ID、中文简繁别名要有独立测试；保留未规范化原文用于展示。

一两个汉字、未知词和缩写要进入专门测试集：名称/别名精确键优先，中文片段按策略产生有界 unigram/bigram 辅助词；不能指望三元组索引完整解决两字词，也不能退化成所有正文 `ILIKE '%字%'`。单字高频词允许提示缩小范围并限额，而不是全库扫描。短语匹配需对原始清洗文本复核；搜索模式展开的词位置不直接等同原文字符偏移。

初选 embedding 基线为 `BAAI/bge-m3`，官方模型卡列出多语言、1024 维和 MIT 许可。用 SentenceTransformers/现成推理框架部署独立服务，版本固定到模型 revision 和 tokenizer revision；不是用聊天模型每次生成答案。基线不代表已经下载、部署或验证中文 MC 效果；发布前必须测模型质量、许可证、硬件和吞吐。是否量化/用 ONNX、是否替换更小模型，由相同评测集决定。

## 正文处理与语义切块

1. 保存原始 Markdown/HTML 的内容哈希和来源版本，按许可保留正文；清洗另建纯文本副本。脚本、导航、样式、隐形内容、远端图片不作为正文词项，不下载/执行嵌入内容。
2. 保留标题和段落结构，先按章节切分，再按已固定 embedding tokenizer 切块。初始实验参数为每块 384–768 tokens、重叠 64 tokens；标题/项目名作为有界上下文附加，计入模型限制。
3. 名称/别名、简介与正文各有字段标签，不能把长正文完全截到简介长度。每块记录字符范围和 token 数；超过处理预算时保留 `truncated`/实际覆盖范围，不宣称全文完整。
4. 原文和当前可发布译文分别切块，保存语言、原文哈希、译文版本、清洗/切块版本。未译文内容可先按原文索引，后续增量添加中文；不会阻塞英文或跨语言搜索。
5. 向量只存当前生效、可发布的块。语义模型不可用时混合搜索明确退化为全文；语义专用查询返回不可用，不能悄悄返回名称结果冒充语义。

词法索引也按有界块建立，避免把所有正文串成超大 `tsvector`。命中片段根据清洗文本偏移提取，不能从分词后的空格串中拼出“原文”。

## 混合搜索决策流程

请求规范化和限制 → 当前可见项目/同一候选版本筛选 → 精确身份召回、全文召回、名称模糊召回、语义召回 → 各路内部按项目归并和排名 → RRF 合并 → 再核对可见性和当前文档版本 → 生成真实片段与游标。

- 精确 ID/来源链接优先定位，模糊相似不得覆盖精确命中。普通名称同名项目仍同时展示。
- 初始每路取最多 200 个候选项目，块过采样有上限；同一项目多个段落、两个语言或多个来源不能重复占位刷高分。具体上限按评测调整。
- RRF 初始实验使用 `sum(weight / (60 + project_rank))`；各路权重、模型、分词、候选大小与可见性策略归入同一个检索配置版本。`ts_rank_cd` 不是 BM25；余弦距离不是正确率，UI 不显示“98% 兼容”。
- 多源项目只有经已确认映射才折叠为一个站内项目，保留全部来源链接。名字相同或向量相近仅能提议人工核验，不能合并包管理身份。
- 索引不是权威依赖清单。搜索结果说“需要某前置”仅表示作者正文有此表述；真实依赖仍查询对应制品的 scan。
